## 完整 HTTP：d40e1940 → 618fe70f

Windows／Ryzen 5 7600X，同机 Go 1.27.2，`GOMAXPROCS=4`、`GOGC=100`、PGO 关闭。
常规场景 `GOMEMLIMIT=2GiB`，图片场景 `8GiB`。客户端、网关、模拟上游分别运行；
五对交替执行，正式计时不采集 profile、不主动 GC。各版本保留生产代码，测试采集器一致。

每个图片场景每版本共 20 个请求（每对 4 个），小请求每版本 1280 个，1024 帧流每版本 160 个。
全部完整消费并通过夹具正文、usage、终态检查；每个场景的上游次数均等于请求数。
真实修改由模拟上游检查修改后的字段，不能用无效或未命中的规则替代。
50 个批次末次恢复采样中的活动请求、日志队列条数、队列载荷均为零。
这只能证明本批次排空，尚不能替代长时运行或强制 GC 后的保留量调查。

**该批次未通过最终性能目标。** 真实修改分配没有下降 50%，延迟没有下降 25%；
SSE 采样堆峰值配对中位数上升约 6.5%。1024 帧耗时五对同向上升，
虽不足 5%，仍须对后续稳定提交复核，不能写成无回退。小样本不发布 P95/P99。
该结果不涵盖 `618fe70f` 之后的提交。

## 后续定位：仍然物化的语义 JSON

在 `0a5d2167` 对应执行代码上，单独运行五次
`BenchmarkReviewRequestBoundaries/json-rule` 分配诊断；它是组件样本，
规则及调用边界与完整 HTTP 不同，约 292 MB/op 不能直接对比上表的完整请求。

profile 显示两个不相交的主要入口是初始 `EncodeSemantic` 和最终
`conversionState.flush` 的 `encodeSemanticWithin`。该采样中前者累计约 481 MiB，
后者约 470 MiB；这些是采样调用链累计分配，不是每请求分配，也不是存活堆。
嵌套 `Value.MarshalJSON`、Compact、编码器扩容以及最终独立字符串占据大头。
父调用与其中 Compact 等子调用的累计值不能相加。

下一步在保留原有 JSON 同步边界和资源检查的前提下，让大核心对象复用已生成的字段读取器，
构造延迟输出计划并只编码最终容器。小对象继续使用现有编码器。
选择条件来自原资源计量，不额外遍历一次正文；非法值和预算错误保留旧诊断路径。
这是移除实现副本的候选，不能在重新配对测量前宣称已取得 HTTP 收益。
