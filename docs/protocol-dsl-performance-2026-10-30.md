# DSL 改造阶段性能记录

本记录属于 `refactor/protocol-dsl` 的阶段验收，整体迁移状态见
[迁移进度](protocol-dsl-migration.md)。四个生产预置尚未切换，不能把基础执行器的改进称为新协议体系已经上线。

## 后续定位：仍然物化的语义 JSON

在 `0a5d2167` 对应执行代码上，单独运行五次
`BenchmarkReviewRequestBoundaries/json-rule` 分配诊断；它是组件样本，
规则及调用边界与完整 HTTP 不同，约 292 MB/op 不能直接对比上表的完整请求。

profile 显示两个不相交的主要入口是初始 `EncodeSemantic` 和最终
`conversionState.flush` 的 `encodeSemanticWithin`。该采样中前者累计约 481 MiB，
后者约 470 MiB；这些是采样调用链累计分配，不是每请求分配，也不是存活堆。
嵌套 `Value.MarshalJSON`、Compact、编码器扩容以及最终独立字符串占据大头。
父调用与其中 Compact 等子调用的累计值不能相加。

`d8a01ce6` 在保留原有 JSON 同步边界和资源检查的前提下，让已通过检查且编码长度
至少 64 KiB 的 Request 复用已有字段读取器，构造延迟输出计划并只编码最终容器。
小对象和其他类型继续使用现有编码器。选择条件来自原资源计量，不额外遍历一次正文；
非法值和预算错误保留旧诊断路径。最终结果独立持有正文，不保存计划或临时片段。

其他架构和不同 Go 版本的标准库兼容路径也不能由本组结果代替。

## 四份未启用草案：组件回退

固定 `981fe4c1`，另测旧 codec 与四份 DSL 草案的请求串接：
`DecodeRequest → 移除根 Native → EncodeRequest`。每场景五对交替，各次 benchmark 计时 1 秒；
准备、编译、预热和完整字节预检在计时外，循环检查成功及输出长度，结束再校验输出和输入隔离。
使用 Go 1.27.2、`GOMAXPROCS=4`、`GOGC=100`、`GOMEMLIMIT=8GiB`，PGO 关闭。
媒体为本地合成的 2 MiB base64 文本，没有供应商调用。80 次运行全部成功，输入及最终输出哈希一致。

**四份草案均未通过性能门槛，不能切换生产。** 部分大请求分配下降不能掩盖耗时回退，
也不能根据“已编译为计划”推断它必然比旧 Go codec 快。

随后独立采集 Anthropic 大请求分配和 Chat 短请求 CPU，未混入配对计时：

- 编码中的 item/binding 读取未设置 valueReader，存在性查询和实际读取分别克隆约 2 MiB。
  相应读取链约 419 MiB 的采样累计分配，与每次约 4.15 MiB 的额外分配相吻合。
- Chat 短请求 CPU 样本中，计划 build 累计 14.32/26.17 CPU 秒，
  sonicObjectMember 为 4.28 秒，gcDrain 为 5.41 秒；父子累计不可相加。
- Native/Provenance 相关函数的样本并集约 2.22%，不足以支持优先重写它们。
  equality 约 3.48%，规范化约 1.26%；大请求的扫描 CPU 尚未单独证明。

下一步先修复读取的所有权边界，再减少重复字段读取。借用优化必须同时验证小根输出、
跨 binding 的小片段不会保留大父体，不能只把 Clone 去掉就算完成。
新增缓存若需要，只能属于一次计划调用，不能改变公开 ReadObject 的独立所有权，
也不能省略重复键、UTF-8、预算、错误顺序或原生来源检查。
