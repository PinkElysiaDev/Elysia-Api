# 协议验证与发布检查

[文档索引](README.md) · [English](protocol-release-readiness.en.md) · [协议指南](protocol-guide.md)

本文说明如何验证当前检出的代码及准备发布。测试结果属于具体提交、配置和运行环境；一次运行的日志、通过数量和临时安排保存在 CI、PR 或本地工作目录，不作为长期功能说明。

## 验证层次

| 层次 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| 协议样例与组合验证 | 指定能力、转换规则、字段存在性及事件关联符合契约 | 真实供应商接受请求 |
| 本地 HTTP、WebSocket、任务与 SQLite 集成 | 路由、权限、取消、持久化、重启及结算行为 | 供应商可用性和生产容量 |
| SDK 与客户端测试 | 固定客户端能完整消费输出并完成工具往返 | 其他版本、插件或历史压缩场景 |
| 真实上游验证 | 指定账号、模型、协议修订和配置下的实际行为 | 所有模型或渠道的兼容性 |
| 缓存与时间实验 | 实际返回的非零计数、资源生命周期和观察窗口 | 仅凭字段接受或 HTTP 200 推断缓存命中 |
| race、fuzz、基准与负载测试 | 选定路径的并发、输入边界和资源成本 | 未测环境下的容量与延迟承诺 |

跳过、预期拒绝、上游限流和未完成的实验分别记录，不能合并为通过。供应商用量与网关估算分开，客户端占位计数不作为真实观测。

## 本地检查

在仓库根目录执行，按改动选择相关检查：

```bash
go -C backend test ./... -count=1 -timeout=15m
go -C backend vet ./...
go -C backend test -race ./protocol/... ./storage ./relay ./server -count=1 -timeout=20m
node scripts/test-protocol-e2e.mjs
```

race 需要受支持的 Go 平台和 C 工具链。浏览器集成使用隔离后端与数据库；环境要求见[开发指南](development.md)。不能因为测试耗时或缺少环境而把未执行项标成通过。

| 改动 | 重点回归 |
| --- | --- |
| 请求参数、模型能力和转换规则 | 四协议 JSON/SSE、严格/兼容策略、候选隔离、Native 保留与输出上限 |
| 工具、思考和签名 | 多工具关联、完整第二轮历史、加密思考、签名作用域与篡改拒绝 |
| 流式 | 开始/结束顺序、usage 尾帧、迟到错误、慢读、取消及无重放 |
| 绑定、修订和升级 | 证据失效、并发更新、失败隔离、草稿保留及重复重启 |
| 会话和任务 | 双向事件、背压、提交不确定、重启恢复和一次结算 |
| 管理界面与 Agent | 保存/验证/启用、并发冲突、精确 JSON 和权限检查 |

负向用例仍须拒绝非法类型、未知机制、资源越界、工具失配及陈旧证据；不能删除断言或缩减能力声明来掩盖错误。

## 真实渠道与缓存

运行方法、配置模板和结果格式见[协议审计工具](../scripts/protocol-audit/README.md)。只对明确选择的账号与模型执行，预先设置请求预算和超时，使用合成内容及隔离实例。

先建立直连基线，再比较网关 JSON/SSE 和工具往返。响应成功后仍检查语义内容、结束状态、隐藏错误事件和用量。供应商限制、客户端消费失败和转换缺陷分别定位。

缓存检查固定账号、模型和足够长的稳定前缀，分别核对非零读取/创建、流式用量以及客户端与 SQLite 的一致性。TTL、读取刷新和显式资源到期需要真实时间窗口；窗口内未观察到失效不等于无限期有效。字段与实验入口见[缓存契约](cache-usage-contracts.md)。

未知原生扩展、不同协议的资源引用、客户端压缩后的签名恢复及供应商专有字段，均需独立样例和实际端点验证。单个渠道通过不扩大整个协议的支持声明。

## 性能与构建

在同一主机、相同输入和并发下比较基准，保留 CPU、内存、分配量、延迟与版本信息。示例：

```bash
go -C backend test ./protocol/builtin -run '^$' -bench 'BenchmarkCacheConversion|BenchmarkStreamTextDecode' -benchmem -count=3
```

容量目标必须在目标硬件和实际负载下测量。旧版本的一次性能报告不能作为当前版本结论。

发行构建见[开发指南](development.md#发行构建)。交叉编译成功只证明构建；各目标系统的启动、数据库升级、UI 和网络行为需单独冒烟。macOS App 检查见[macOS 验证](macos-testing.md)。

## 升级与回滚

1. 保留旧程序，以及同一时间点的配置、数据库和匹配主密钥。停止写入后复制，或使用一致的 SQLite 备份；不要遗漏 WAL 中的数据。
2. 本版本不提供旧 schema 或配置的兼容和迁移。使用当前格式初始化环境，通过当前管理接口重建必要记录并处理定义、绑定诊断。
3. 内置预置随程序更新；定制内容应保存在独立 ID 的协议中。检查自定义修订、草稿、显式未绑定状态和重复重启行为。
4. 核对协议接口的 `runtimeReady`、有效绑定和实际请求。仅 `/health` 返回成功不足以证明协议可用。
5. 协议修订回滚仍须通过当前引擎验证。程序/数据库回滚则恢复匹配的旧程序、数据库、配置和主密钥；先保留当前数据库，避免丢失备份后的记录。

`git revert` 不会恢复已写入的数据。升级约束见[部署指南](deployment.md#升级备份与恢复)，当前协议恢复见[预置恢复](protocol-preset-recovery.md)。
