# 本轮修复前后详细性能对比

## 结论

对比 **`306cf079 / dev.76` → `8d7998c3 / dev.77`**。本轮修复启动日志、Responses 辅助 metadata、下游交付归因及最终日志结算。

**正常成功路径的累计分配基本持平，没有出现成倍膨胀；时延有小幅变化和明显的样本波动。慢发送时，日志资产的存活时间确实增加，这是本轮最明确的内存代价。**

- 五个正常场景的累计分配中位变化为 **−0.08%～+0.64%**；完整消费时延中位变化为 **−2.69%～+6.68%**。这里的百分比为“两版中位数之比”，不是每一对变化的中位数。
- 短 Chat CPU 从 **0.6638 → 0.7133 ms/请求，+7.47%**，没有同等幅度的客户端时延增长。现有数据不足以把全部差异归因到某个新函数。
- 31 MiB、不保存正文的堆峰值首轮中位 **250.00 → 294.61 MiB，+17.84%**；独立五对确认 **294.67 → 294.63 MiB，−0.01%**。没有稳定复现首轮增幅，也不能因此宣称峰值下降。
- 最后发送停滞时，单份31 MiB请求日志夹具约额外持有 **31.12 MiB**，媒体外置约额外持有 **23.12 MiB**。发送和日志写入完成、主动GC后，新旧保留量接近；这不是完整生产记录的增量上限。
- 四并发取消和连续运行实验没有观察到持续增长；这只代表有限本地实验，不是长期生产无泄漏证明。

本报告重新整理既有原始测量，没有重跑负载或修改生产代码。旧长报告漏写最终结果的问题已补齐；旧草稿另存，原始样本不覆盖。

### 各指标表示什么

- **完整消费时延**：客户端发出请求到读完响应的墙钟时间。表中先取每轮请求P50，再取五轮中位；模拟供应商没有真实模型生成时间。
- **CPU时间**：网关进程在测量期间累计CPU时间，除以请求数，再取五轮中位。包含GC及结算等工作，不是某一个转换函数的耗时。多核累计CPU可高于墙钟时间。
- **累计分配**：期间申请过的内存总字节，包括后来已回收的对象。资源采样在日志结算完成后读取；客户端时延不等待异步日志最终落库，因此两者边界并不完全相同。
- **采样堆峰值**：测量窗口中观察到的Go堆最大值，随后取五轮中位；不是每请求净增量，也不保证抓住真实最高点。
- **采样工作集峰值**：Windows观察到的网关驻留物理内存，包含堆之外的运行时、代码、栈等；不能与堆峰值相加。

以上内存指标都不是固态硬盘容量。小请求场景的堆/工作集是整个4096请求运行窗口的进程峰值，不能除以4096解释成单请求占用。

## 4. 慢发送：新增内存代价发生在哪里

### 为什么多保留一份日志

旧版在handler结束时提交日志，有时尚未执行最终发送。新版在该时点完成脱敏、媒体提取、正文物化并释放原始捕获缓冲，但要等最终Write/Flush/Finalize结果才能提交一次正确的最终记录。

因此，在“业务处理已结束，最后发送仍卡住”的窗口里，**新版必须继续持有待提交的日志正文/媒体**。旧版在同一窗口可能已经写库并释放。它没有增加一次生成、第二次日志SQL更新或整轮流事件缓存，却延长了这批资产的存活时间。

代码入口是[HTTP结算](../backend/server/http_usage.go:8)、[交付状态](../backend/server/http_delivery.go:34)、[日志准备与写入](../backend/server/usage.go:350)。

### 独立所有权实验

每场景五对，每次五批。普通ExtWriter gate让最终发送停住，先排空允许提前提交的日志，再观察存活量。实验包含客户端和合成输入、没有请求转换和模拟供应商；主动GC用于排除不可达垃圾。因此它是所有权实验，**不能当作独立网关峰值**。

夹具只构造一份大请求日志及很小的响应。完整网关日志还可能同时保存出站请求等其他正文，因此这里的31/23 MiB不能当作所有生产请求的额外占用上限；实际取决于整条记录持有的最终资产总量。

| 场景 | 发送停滞、GC后 MiB：前→后 | 新版额外保留 | 发送及写入完成、GC后 MiB：前→后 |
|---|---:|---:|---:|
| 31 MiB，日志关闭 | 33.35 → 33.20 | 约0 | 33.20 → 33.35 |
| 31 MiB，保存正文 | 33.20 → 64.32 | **+31.12 MiB** | 33.24 → 33.22 |
| 31 MiB，媒体外置 | 33.57 → 56.68 | **+23.12 MiB** | 33.21 → 33.36 |
| 2 MiB×4，正文保存后取消 | 4.39 → 12.45 | **+8.06 MiB** | 4.24 → 4.32 |

![慢Finalize的持有与释放](../.tmp-dev/metadata-delivery-comparison-2026-10-23/slow-finalize-retention.png)

31 MiB base64文本对应约23.25 MiB解码媒体载荷，因此媒体外置后待提交资产仍然很大。实验测得的堆差额约23.12 MiB，不把它强行写成与载荷字节精确相等。

新版所有批次的原始`captureBytes`为0；发送及写入完成后，活动请求和排队字节均归零。保留的是整理后的日志资产，不是多留原始捕获缓冲。

**这部分属于活跃请求内存，不受128 MiB异步日志队列预算保护。** 如果更多请求同时堵在最终发送处，资产可叠加。按本实验每条记录仅含一份约31/23 MiB大载荷线性估计，四个类似阻塞请求可能多持有约124/92 MiB日志载荷；这是估算，不是31 MiB四并发实测，也不是完整生产记录或整个进程的上限。

### GC前后的数字不能混用

保存正文实验在发送完成后、没有再额外GC时，旧/新读数为33.24/175.09 MiB；再主动GC后为33.24/33.22 MiB。这里旧版日志处理发生在held阶段GC之前，新版日志处理发生在其后，所以两者未回收垃圾量不同。

这个现象不能证明额外142 MiB仍被请求引用，也不能承诺实际进程会马上把这部分物理内存归还系统。所谓“释放后未额外GC”仍处于一个此前主动GC过的诊断实验中，不能拿它替代完全自然运行的峰值测试。

最初的日志关闭实验还暴露了夹具问题：排队字节为0时，零载荷记录可能已被worker取走但尚未落库。测试现已额外等待`Written`达到预期数量并校验数据库精确记录数。失败保存在原目录，正式所有权结果来自修正后的`retention-v2`；生产实现没有因此变化。

## 5. 取消与连续运行

### 四并发取消

2 MiB图片/工具历史、四并发、五对，每次五批，每版本100次请求。客户端收到真实SSE事件后取消，网关和供应商独立进程。

|---|---:|---:|---:|
| 累计分配 MiB/请求 | 17.2913 | 17.2575 | 约−0.20% |
| 每批网关采样堆峰值 MiB | 55.7969 | 55.6373 | 约−0.29% |
| 取消排空并主动GC后，网关堆 MiB | 3.3491 | 3.3510 | 约+0.002 MiB |
| 活动请求/队列/排队载荷 | 全部归零 | 全部归零 | 无残留活动工作 |
| 回收后goroutine观察 | 各批13 | 各批13 | 未逐批增长 |

每批上游调用数与请求数相等，没有重复生成。表中按每次五批中位再取五次中位；取消实验含主动GC，与正常响应时延测试分开。这些结果没有提供“取消时延快了多少”的独立数字。

| 保存正文，5轮 | 225.29～363.20 | 256.43～363.32 | 723.04～772.56 | 739.44～748.03 |

## 6. 哪些成本是本轮新增，哪些仍是既有问题

| 修改/行为 | 能支持的判断 | 尚不能证明的内容 |
|---|---|---|
| 请求级交付状态、错误证据、最终结算回调 | 正常路径增加少量分配；失败路径正确性改善有回归证据 | 未用单因素profile分离每个字段/回调的CPU成本 |
| 延迟提交最终日志 | 慢Finalize额外保留31/23 MiB有明确所有权实验支持 | 未测真实客户端慢读分布，不能估算生产同时持有多少记录 |
| metadata新分派 | 正确接受辅助帧、保留原生字节并按策略投影；只处理当前帧 | 旧版提前失败，不能与新版完整成功相比来算“提速” |
| 启动日志分类 | 维持验证、事务复核及发布顺序 | 没有专门的启动五对测量，不宣称启动变快 |
| Hertz精确去重 | 避免同一已记录类型化错误重复输出，有功能测试 | 未做高错误率日志吞吐量基准，不给CPU节省百分比 |
| 正文日志开销 | 新版31 MiB样本关闭/保存/媒体外置分配分别259.50/866.92/407.03 MiB | 未在本轮新采profile，不能按这些总数直接指定内部热点函数 |

在同一个新版本里，保存正文相对日志关闭多分配约 **607.42 MiB/请求**，媒体外置多约 **147.53 MiB/请求**；旧版同样存在接近的差额。这是本批尚未消除的日志处理成本，不是此次修复新增的同等成本。累计分配差额不能解释为同时额外占用607 MiB。

另一个值得后续分析的量是：1024帧流每请求约49.3万个分配对象；正文日志大图约10万个，日志关闭约4661个。这些是后续定位线索，需要新profile和等价性验证后才能制定具体代码优化，不能只凭对象数删验证或改变日志语义。

## 7. 验收结论和未覆盖项

按计划中的“正常成功路径中位时延/分配回退超过10%需要复核”门槛，本次五个主场景没有触发；额外对大图堆峰值进行了独立确认。CPU、工作集和存活阶段的差异分别保留，没有把它们混成“整体性能提升”。

当前可以支持的判断是：**普通请求的大正文累计分配未明显增加；部分时延/CPU变化尚受波动影响；慢发送日志的存活内存明确增加，但结束后的回收与取消生命周期没有观察到持续增长。** 本批没有证据支持“整个项目明显更快”或“内存完全不变”。

工程验收：相关race、vet、161项审计、30项页面测试、前端检查和六目标构建通过。Go全量仅保留既有A2A淘汰测试失败，旧二进制同样复现；固定staticcheck v0.8.2保留45条既有诊断，新增0，不能称为全部工程检查通过。

未覆盖：真实供应商和原长会话客户端、31 MiB四并发、正常请求32并发、其他平台运行、新metadata成功路径的独立性能基准、启动速度、错误风暴下日志吞吐量和长期生产保留量。没有新采CPU/分配火焰图，图中内容均为已有测量的对比，不冒充函数级归因。
