# v1.6.2 与当前后端的 profiling 对比

采集日期：2026-10-20。基线为发布 tag `v1.6.2`（`8f50807c295f9d6f2669d79794e58c89188722b3`），当前版本为 `5a8115e7008e1c9f6035629bbeb58ad119bc2a43`。

**结论：当前版本显著减少了短请求分配，并在本轮完整 HTTP 场景中降低了延迟；但常态驻留及采样峰值内存没有同步改善，不能称为全面的内存优化完成。** 主矩阵 20 项与旧 profiling 补充的 5 项对照全部通过，两版各有 5,615 次正式计数内请求；另保留独立预热、CPU／分配采样和取消诊断。

归档迁入默认分支 `deploy`，基于上游 `8e3c62a`（已合入 `5a8115e`，源码树一致）。采样源版本仍为上面的两个提交，不随默认分支后续更新而改变。

## 比较方法

v1.6.2 中的 `docs/audit-conversion-flamegraphs-dev72.md` 和 `docs/artifacts/conversion-flamegraphs-dev72/` 是本轮场景和热点参考。旧归档实际采自 `31ea3a9`，环境是 Windows/amd64、Go 1.26.5、Ryzen 5 7600X、默认 GOMAXPROCS、8 GiB GOMEMLIMIT。本轮不将它与 Linux 新测耗时直接相除，也不把旧归档当作 tag `v1.6.2` 的本机测量。

两版在同一台 Linux/amd64、AMD Ryzen 7 8845H、8 个逻辑 CPU、32 GiB 内存的机器串行重测：

- Go 1.27.2，`GOMAXPROCS=4`、`GOGC=100`、`GOMEMLIMIT=2GiB`，`-pgo=off`。
- v1.6.2 保留原生产依赖和默认标准 JSON 构建；当前版本使用项目要求的 `-tags=sonic`。这是**整版本**比较，包含 JSON 实现、依赖升级及其他重构的共同影响，不单独归因于某一个优化提交。
- 旧 Sonic 1.11.6 的 loader 不支持 Go 1.27；强制给 v1.6.2 加 `sonic` tag 的初次试跑构建失败，保留失败日志。未通过升级旧版生产依赖来绕过问题。
- 将当前四个 HTTP profiling `_test.go` 采集器回移到独立的 v1.6.2 worktree，仅使用该版原生的标准 JSON API，并增加测试专用 writer 统计适配。适配通过成功提交后递增的 `usageSeq` 和受锁保护的队列状态等待落库；不停止／重启 writer，不强制 GC。旧版生产源码及 `go.mod`、`go.sum` 不修改。
- 客户端、网关和 provider 为三个进程；CPU、分配、GC、堆及 RSS 只计网关子进程。测试采集器和后台运行时的小量开销仍在计数内；两版采集器的 JSON 实现不同，尤其不能把很小的差值解释成纯业务优化。
- 所有请求完整消费并验证文本、usage 和上游调用次数；协议矩阵还验证历史文本与工具定义保留。无真实账户、真实供应商或生产数据库。

### 负载与统计口径

主矩阵沿用 [后端性能基准](backend-performance.md) 的全部 20 个场景：常规每轮 64 次请求、5 轮、4 次预热；图片每轮固定 4 次、重载每轮固定 1 次，不受 `--requests=64` 覆盖。每轮结算后自然空闲观察 1 秒，保存 0%、10%、50%、100% 恢复点及 20 ms 采样时间线。

另外沿用旧 profiling 的 1,800 文本块、512 小增量和 31 MiB base64 图片／工具历史：文本块每轮 4 次，事件每轮 16 次，31 MiB 图片每轮 1 次，均 5 轮、4 次预热；文本块和图片分别测 JSON/SSE。31 MiB 只运行单并发，没有将它描述为 31 MiB 四并发验收。

CPU 与 memory 独立运行；CPU 每场景 30 秒。正式 HTTP 计时不启用 profiler、不主动 GC。memory 运行在测量前 GC、排空后再 GC 两次，分配 profile 使用 before/after 差分；其计时不参与正式性能结论。`heap-active` 是启动后约 250 ms 的定时快照，不是峰值触发。

表格使用各轮指标的中位数；峰值堆和 RSS 使用各轮**绝对采样峰值的最大值**。P50 是完整消费响应的延迟，不包含响应结束后的 usage 落库等待；CPU／分配则计至 usage 结算。闭环吞吐包含客户端校验成本，不是网关的极限 QPS。小样本尤其图片与重载的 P95/P99 不作生产尾延迟结论。

两版按整组顺序采集，不是随机交替 A/B，也没有隔离机器上其他正常服务。微基准原始耗时存在明显轮间波动；本报告记录观察值，不宣称这些差值已通过统计显著性检验，不把整版本收益归给一个函数或单一提交。

采样峰值可能漏掉短尖峰。HeapAlloc 含未 GC 垃圾，不等于精确存活对象；1 秒自然空闲不会保证立即 GC 或归还 RSS。CPU cumulative 热点有包含关系，不能相加；`alloc_space` 是累计申请，不是峰值内存。

| --- | ---: | ---: |

独立取消诊断两版均通过：2 MiB × 4 并发 × 5 批，强制 GC 后旧版堆为 2.700～2.702 MiB，当前为 3.617～3.628 MiB；活动请求均回到 0，goroutine 各自稳定为 9／12。它没有显示这五批中的持续大载荷堆积，但 RSS 仍分别处于约 138.6～159.1／162.6～184.8 MiB；**不是长时无泄漏证明，也不是操作系统已归还所有内存的证明**。

## CPU 与分配热点

共 6 场景 × 2 版，各采集一份 30 秒 CPU profile，累计 CPU 样本为 23.78～39.50 秒，全部超过 10 秒。多线程累计 CPU 可以超过 30 秒；不同版本在窗口内完成的请求数不同，不能比较整份 profile 的总 CPU 样本量来判断单请求退化。

### 扫描热点已改变，不是扫描检查被删除

下表是全网关 CPU 的 **flat（函数自身）占比**：

| 场景 | `jsonStringEnd` 旧 → 新 | `typedMeter.scanRaw` 旧 → 新 |
| --- | ---: | ---: |
| 2 MiB 图片 | 47.28% → 0.051% | 28.95% → 0.10% |
| 31 MiB 图片 | 47.03% → 0%（自身未采到） | 34.41% → 0%（自身未采到） |
| 1,800 文本块 | 33.33% → 0.85% | 21.87% → 0.74% |
| 512 小增量 | 1.61% → 0.62% | 0.68% → 0.47% |

当前 [`value_container.go`](../backend/protocol/value_container.go) 使用批量引号定位，[`typed_limits.go`](../backend/protocol/typed_limits.go) 使用批量计数及 UTF-8 校验。因此不能把上述 flat 的下降描述成检查成本归零：31 MiB 的 `scanRaw` **cumulative 仍占 24.90%**，`jsonStringEnd` cumulative 仍占 9.49%，两者可能嵌套，不能相加。

31 MiB 当前图中，`indexbytebody`、`countbody`、`utf8.ValidString` 自身分别占 28.39%、10.72%、6.91%，`runtime.memmove` 占 16.00%。2 MiB 当前图中，`runtime.memmove` 自身占 17.22%，`runtime.gcDrain` 子树占 20.77%。这些比例的分母是各自 profile；不能把占比变大直接解释为每请求复制或 GC 绝对时间增加。

### 图片分配仍集中于复制和容器物化

当前 2 MiB 图片的独立 memory 运行含 4 次请求，before/after 差分约 419.17 MiB 采样累计分配。前三个自身分配位置是：

| 分配位置 | 采样分配 MiB | 自身占比 |
| --- | ---: | ---: |
| `internal/stringslite.Clone` | 153.35 | 36.58% |
| `internal/bytealg.MakeNoZero` | 151.31 | 36.10% |
| `protocol.ParseValue` | 57.25 | 13.66% |

调用子树中 `Compiled.EncodeRequest` 占 39.77%，`preserveMappedNative` 占 21.23%，`ValidateWireOutput` 占 27.58%；这些子树有包含关系，不相加。`wire_contract.go` 的 `readWireObject` 仍使用复制式 `ReadObject`，`value_encode.go` 仍逐层构造容器输出。旧报告提出的最终校验读取和多层物化问题仍值得优先处理。

该差分还包含 profile 采集器自身开销，例如 `runtime/pprof.writeHeapInternal` 子树约 8.34 MiB；不将采样总量／请求数冒充正式 B/request，也不减去估计值再宣称精确分配。

### 长流仍有显著的逐帧成本

当前 256 帧同协议请求约 **113,415 allocs/request**，跨协议约 **157,122**；1024 帧约 **440,964**。即使短请求的执行计划和所有权复用已有效，逐帧语义处理、规范化、编码与最终校验仍会累积大量小分配。当前 256 帧 CPU 中系统调用自身占 13.42%、GC drain 子树占 17.17%；不能只根据系统调用占比认定数据库或网络等待是瓶颈，更不能据此直接修改 flush 语义。

23 项两版共有微基准均各运行 5 次、每次 300 ms。下面为中位数；`RuntimeSchema` 等只有当前版具备的项目不做伪配对。原始日志可进一步用于 `benchstat`，本轮未进行显著性检验。

| TypedResourceCheck/structural | 151205 → 8951 | 0 → 0 | 0 → 0 |
| TypedResourceCheck/encoding | 1867486 → 1231630 | 352904 → 371304 | 13 → 15 |

## 下一步优先级与边界

1. **大载荷的复制读取和容器物化**：围绕最终 wire 校验、原生协调和 continuation 提取建立独占／只读访问边界，减少大字符串重复复制。继续保留最终正文检查、精确数字比较、未知字段保护、资源预算和可变容器隔离；不以删除校验换收益。
2. **长流逐帧分配**：分解 typed 事件、规范化、native digest、编码及最终验证的成本。先定具体阶段预算，不能把整请求分配除以帧数冒充纯 decoder 成本。
3. **常态驻留与回收**：单独调查当前额外的 RSS／堆、长时 usage 日志及更长空闲曲线，结合强制 GC 的归因实验定位保留者；本轮不能把它们直接判成泄漏，也不能排除泄漏。
4. **微基准及重载回退复核**：优先复核上面的 Responses/tools32、声明式短请求、stream decode 分配和单请求 CPU；本轮不改生产行为，也不以局部 zero-allocation 目标代替完整 HTTP 验收。

本轮没有完成 16 协议组合的完整旧矩阵、31 MiB 四并发、长时日志稳定性、真实供应商、原生跨平台或全量单元测试／race 回归，不将本次 profiling 通过描述成这些验收通过。
