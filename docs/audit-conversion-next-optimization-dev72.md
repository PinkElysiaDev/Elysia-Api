# 转换链路下一批优化计划：基于火焰图与处理账本

调查基线：`31ea3a9`，编译器 `2.0.0-dev.72`。依据：[调查报告](audit-conversion-flamegraphs-dev72.md)、[图册](artifacts/conversion-flamegraphs-dev72/index.html)、[逐次结果与计数](artifacts/conversion-flamegraphs-dev72/summary.json)。本文件是下一批实施方案，本轮没有把其中的性能原型接入生产。

## 1. 先改什么

剩余成本有两类：CPU 不断扫描不变的大字符串；内存则不断构造父子 JSON 容器、校验副本及比较树。默认规则段已经共享解析对象，继续机械提取规则函数无法解决这些热点。

| 顺序 | 修改范围 | 现有证据 | 收益与风险判断 |
|---|---|---|---|
| 1 | 最终校验、媒体读取的局部借用视图 | 2 MiB 请求的最终线格式校验复制片段合计 26.002 MiB；整个 HTTP 的片段复制约 38.85 MiB | 直接削减多层复制，范围较局部；必须控制引用寿命 |
| 2 | 字符串一次扫描，复用不可变计量事实 | 31 MiB 的两个扫描函数自身合计约 70% CPU；局部原型快约 37.8% | CPU 优先项，扫描器边界风险高，先做完整等价验证 |
| 3 | 原生协调的局部语义比较 | 2 MiB 分配 profile 的 `equalValues` 调用子树约 25.87 MiB | 避免整树解码；精确数字、重复键及转义语义必须不变 |
| 4 | 容器输出延迟物化 | 编码账本：31 MiB 图片穿过 8 层容器，两套投影合计输出约 496 MiB | 大载荷绝对成本高，但影响编码边界，独立批次实施 |
| 5 | 多候选的不可变准备结果复用 | 2 MiB 的 1→4→16 候选使分配近似随候选数增长；真正上游命中仍为 1 | 不能删除资格预检；只复用可证明上下文一致的纯计算 |
| 后续 | 通用映射与小事件 | 一条通用边界使 24 KiB 编解码分配约 0.992→5.17 MiB；事件段存在独立 JSON 往返 | 必要同步不能省略；先证明特定路径再接入，不并入大载荷重构 |

上述分配数字有包含关系，不相加承诺总收益。容器成本绝对量很大，排在后面是因为改动风险更高。PGO 继续暂停，待结构成本稳定且有代表性训练负载后另行评估。

## 2. 第一步：校验照做，改成在请求内读取同一份正文

代码入口：[`builtin/wire_contract.go`](../backend/protocol/builtin/wire_contract.go)、[`value_reader.go`](../backend/protocol/value_reader.go)、媒体编码及续传提取调用者。

目前 `validateRequestWireContract` 在最终检查中调用 `adapter.decodeRequest(value, EvaluationContext{})`。这个上下文没有请求读取视图，`ReadObject` 会为子对象复制字符串；仅验证工具关联也因此重建多层快照。完整 HTTP 的其他复制来自媒体编码、续传载体提取和 `continuationSession`，须分开登记。

实施方式：

1. 给最终内置线格式校验建立调用内只读读取上下文。保留原字段验证、重新解码和工具关联验证的执行顺序；校验看到的是当前最终正文，包括用户 `after` 的修改。
2. 内置校验助手显式接受该上下文。公共 `Value.ReadObject`、`ReadArray`、`Bytes` 仍维持复制契约，不改变所有调用者。
3. 媒体编码读取快照时仅在受控请求生命周期内借用；修改 map/slice 前仍建立独立所有权。
4. 续传提取另立提交：先梳理哪些 ID、签名和载体要跨请求保留，在写入长期状态前独立复制。不能让几十字节的 ID 挂住 31 MiB 根字符串。
5. 不复用此前校验的“通过”结论，不删除最终验证，不把物理共享当作资源计数去重。

差分：四协议，重复键、转义键、非法字段、工具关联、未知扩展、缓存边界；`after` 新增非法字段必须仍在最终输出阶段拒绝。比较首个错误、路径、诊断顺序及完整输出字节。并发候选共享原值但不共享可变容器。

验收指标：同一 2 MiB 夹具，最终校验账本的 `view.copy` 由 26.002 MiB 降到不超过 2 MiB；复制不能转移到另一个无计数的解析器。HTTP 总分配、峰值及取消后保留量另外实测。保留小字段释放根正文的测试必须通过。

## 3. 第二步：合并扫描，再研究跨边界计量复用

代码入口：[`typed_limits.go`](../backend/protocol/typed_limits.go)、[`conversion_state.go`](../backend/protocol/conversion_state.go)、[`semantic_cache.go`](../backend/protocol/semantic_cache.go)、[`value_container.go`](../backend/protocol/value_container.go)。

先做范围较小的扫描器替换：在寻找字符串终点时同时统计原始长度、编码长度和需要规范化的特征。不能为了快而先跳到结尾，再回头扫描；也不能假设所有长字符串都是 base64。

本轮 `_test.go` 中的原型仅证明合法字符串 token 的局部结果一致。10 秒 fuzz 不能替代完整资源检查，接入前还需验证：

- 反斜线、引号、HTML 字符、U+2028/U+2029、Unicode 转义、非法 UTF-8、截断转义、数字及对象边界。
- 字节、节点、深度恰好等于限额及超出时的数量、路径与首个错误一致。
- 大字符串中间取消，整数溢出、扫描步数和错误链一致；不能推迟取消检查到字符串末尾。
- 规范化时机不变，保留空集合省略、nil/null、数字拼写和原生字节。

验收指标：2／31 MiB 长 token 的局部扫描中位耗时降低至少 25%，零额外分配；小 token 不回退超过 10%。本轮原型约 37.8% 的收益只是可行性证据，不是 HTTP 收益。接入后必须重新采集完整 CPU 图及五次配对 HTTP 结果。

随后单独研究跨解码、转换、编码边界共享不可变计量事实：只缓存字节数、编码长度、相对深度、节点数和规范化性质。每次放置仍累加，每个阶段仍用自己的有效限额、路径和错误包装。缓存不能保存“此值在所有上下文均合法”的结论。

复用绑定同次调用、原值和相关规范化规则；通用修改后重新识别，条数及保留字节受现有限制约束。超限或无法证明时走原检查路径，不能新增拒绝。不引入 `unsafe`、跨请求缓存、全文摘要或公共 `Value` 身份体系。

这一子项先在诊断账本中证明减少了实际 `scanRaw` 和字符串扫描次数，目标为重点夹具的重复计量扫描字节至少减少 30%，同时保持逐规则检查次数。达不到或错误顺序变化时暂不接入。全值哈希虽然有成本，但 2 MiB 命中约 26 微秒，远小于数毫秒扫描，不优先改缓存键机制。

## 4. 第三步：比较 JSON 时不要先展开两棵大树

代码入口：[`native_reconcile.go`](../backend/protocol/native_reconcile.go) 的 `equalNativeValues`，以及 [`value_schema.go`](../backend/protocol/value_schema.go) 的原比较定义。

现有原值相同、根小字段不同的快速判断保留。对其余对象／数组，使用请求内只读子值递归比较：键集合、数组位置和相同原值可直接判断；只有确实需要比较的叶子才解码。数值继续用原有精确数字语义，不能以 float64 或字符串相等代替 `1 == 1.0`。

先给原比较器建立测试 oracle，再覆盖键顺序、重复键最后值、转义字符串、巨大整数、指数、负零、null/缺失、未知扩展、深嵌套、非法值及数组身份。未证明的分支预先选择旧实现；不能部分修改后失败重跑。

验收指标：2 MiB 夹具 `equalNativeValues` 子树分配下降至少 80%，不再按图片大小解码整棵树；正确性比较仍逐项执行。协调后的原生字节和签名摘要必须完全相同。该收益包含在编码阶段内，不能重复加到“编码节省”上。

## 5. 第四步：避免八层容器各保存一份完整图片

代码入口：[`value_encode.go`](../backend/protocol/value_encode.go)、内置块／消息编码器、[`runtime.go`](../backend/protocol/runtime.go) 的原生保护回放。

目前八层依次是：媒体 source、图片块、工具结果 content 数组、工具结果对象、消息 content 数组、消息对象、messages 数组、请求对象。当前投影和基线投影各构造一次。只改模型与完全不改模型都出现这条链。

限定实现：在内置请求编码内部建立有界的输出片段／容器计划。叶子引用已有不可变 JSON，父容器记录顺序、键和长度，根输出时一次写入。不要把这个计划变成新的公共 JSON 类型或通用转换框架。

长度计算、溢出和资源拒绝发生在分配前；保留排序、HTML 转义、规范化和缺失值错误。遇到通用 mapping、`initial/after` 或原生协调需要真实值的边界，按需物化，不能越过可观察边界延迟错误。每份输出计划只属于当前候选／编码调用，不能长期缓存大根对象。

原生协调的“原始语义投影”和“当前投影”职责仍保留。首版可以各物化一次根输出，不要求一次性合并协调算法，也不改变数组身份匹配。中间容器节点不保存自己的完整字符串。

验收指标：31 MiB 编码夹具大容器物化由 16 次降到不超过 4 个完整载荷当量，账本大容器输出由约 496 MiB 降到不超过 124 MiB。这是该子项的接入门槛，不是已实现收益；若原生边界需要更多次，先解释必要性，不能为了达标绕过保护。2／8／16／31 MiB 的分配必须近似线性，四并发在原环境门槛满足后验收。

## 6. 多候选、通用映射与事件的独立后续工作

多候选：现有“首候选编码结果复用”没有消除其余候选的预检成本。先分解每个候选的解码、规则、编码和资格检查，不删除任何候选的诊断或改变错误优先级。仅当协议固定修订、模型、scope、策略、预算、上下文及缓存意图都一致时，复用纯计算产物；动态用户映射不能按协议名称判定相等。候选结果用完释放，不保存 16 份正文。验收同时比较 1／4／16 候选的每候选工作量、峰值和错误顺序，上游调用次数不得增加。

通用映射：本轮 `set-same`、`set-changed` 和 JSON 条件都明显贵于 typed 路径，但这不能证明同步无意义。逐条条件必须看到前序修改，JSON 边界也影响规范化。先统计 `flush/load` 对及产生它们的具体规则；只删除没有消费者、没有可观察规范化和错误顺序作用的重复同步。数据依赖未证明时保留旧路径。`after` 和手写映射目前只做后续定向分析，不宣称已获得同等覆盖。

事件：512 个小增量场景中 `CompiledConversion.Event` 累计约 16.2%～17.8% CPU；Windows `WSASend` 的 flush 调用也占显著样本。先把逐事件 `EncodeSemantic → load → flush → decode` 与网络写分开测。typed 事件入口的独立对象、规范化、晚到 usage、终止校验及每帧检查保持不变；不能把一轮事件攒到内存后再发。网络合并写可能改变首字延迟和取消时机，需单独 trace 与客户端延迟证据，本计划不直接修改 flush 行为。

## 7. 差分与验收顺序

1. 固定本轮输入、字节级 oracle、采样工具和基准二进制。每项性能改动单独提交，基于实际最终提交重测。
2. 保留四协议 JSON/SSE、严格／兼容／规则禁用、工具后续、思考签名、usage、异常结束、取消及未知字段测试。响应和事件不能因请求共享底层改动而退化。
3. 完整比较输出字节、SSE 顺序、诊断顺序与归属、错误链、原生快照、签名／摘要、usage、调用者输入和候选隔离。出现差异停止接入，不修改期望把差异变成通过。
4. 先跑局部计数和分配，再跑完整 HTTP。新旧相同机器、Go 1.26.5、`GOGC=100`、`GOMEMLIMIT=8GiB`、日志配置、分离进程；每组至少五次交替配对，无主动 GC 的正式计时与 GC 保留实验分开。
5. 大请求四并发仍需剩余承诺额度 16 GiB、物理可用 12 GiB；不足标记阻塞，不调页面文件、不降并发代替。补齐本轮未完成的 16／31 MiB 单并发、8／31 MiB 四并发及 31 MiB 日志场景；8 MiB 单并发正式耗时与峰值已有基线。
6. 增加存活阶段观察：最终校验前后、协调比较前后、候选释放后、日志排空后、取消后。Go 堆、累计分配和工作集分别报告；工作集增长另查 SQLite／系统分配，不能只凭 Go 堆说无泄漏。
7. 最终同一代码提交完成 Go 全量、vet、固定 staticcheck、相关 race、审计自测、前端检查／构建、本地页面及六目标构建。失败、跳过和环境阻塞单列。

编译器暂保持 dev.72，仅允许行为等价重构；如果必须更改验证语义，拆出正确性修复并另行升级及重验证据。保留资源预算、默认规则、所有原生保护与用户配置，不加内存准入、不降并发、不关闭日志获取收益。真实供应商及原用户长对话客户端验收另行进行。
