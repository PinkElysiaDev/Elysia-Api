- CPU 火焰图的宽度代表 CPU 采样时间，横向位置不是请求的执行时间线。父函数包含子函数，不能把二者累计百分比相加。

## 已确认的代码行为

### 1. 大图片首先消耗在重复读取，而非规则业务动作

`typedMeter.scanRaw` 对 JSON 字符串先调用 `jsonStringEnd` 找结束引号，随后再次遍历字符串计算 HTML 和行分隔符转义后的长度。对基本无需转义的 base64 文本，这仍然是两轮串行扫描。

`needsSemanticCompaction` 也先寻找结束引号，再检查 `<>&` 和两个 Unicode 行分隔符。它经常是在证明“这段字符串无需改动”，但证明本身依然随图片大小增长。

资源检查是必要的；当前浪费是为多处检查反复求同一个不可变值的性质。不同预算、字段深度和错误阶段仍须分别判断，不能直接删掉检查。

### 2. 缓存有收益，但缓存命中不是零成本

规则段内的 `semanticCache` 已经减少重复计量，不能再把当前实现描述为每条规则完整复制一份请求。缓存以 `Value` 为键，键中的大字符串可能需要哈希或比较；这些成本由 CPU profile 和单独实验核对，不把“传入缓存的键长度”冒充实际哈希字节数。

模块入口、转换入口和原生协调中的部分检查使用不同计量器，未共享同一轮计量结果。这是剩余重复扫描的重要候选来源。

### 3. 每条规则后仍有结构遍历和规范化

即便规则只检查一个小字段，执行器仍会遍历语义容器执行预算检查和边界规范化。大 payload 可以命中不可变值缓存，但 map、slice、指针和字段仍逐个访问。

因此，“一张大图”和“相同文字量拆成 1,800 个节点”需要不同的优化：前者先看扫描，后者还要看反射、容器遍历和小对象分配。不能仅凭规则业务没有修改就跳过空容器省略、转义等旧边界行为。

### 4. 单层编码已优化，父子层仍会复制载荷

`encodeValueContainer` 已能预分配一个容器的输出，但内层容器先成为完整 JSON 字符串，再写入外层容器。图片可以随图片块、工具结果、消息和请求逐层写入新缓冲。

原生协调已复用原始解析基线，但还要编码“原始语义投影”和“本次新投影”，再把真实变化合并回原文。因此，仅修改模型名也不意味着只复制几个字符。保护未知字段和工具数组身份的功能必须保留；可优化的是中间投影的构造方式。

### 5. 通用规则与流事件有独立成本

带 JSON 路径条件或通用操作的请求会进入 JSON 同步边界；原规则顺序及匹配必须观察前序修改，不能一律把同步推迟到末尾。

响应、事件入口仍有语义编码和出口解码。小事件重复几百次后，固定的分配、解析和校验成本会累积；它与大图片的长字符串扫描不是同一个问题。

## 用通俗的话解释这次发现

可以把请求想成一本夹着大照片的文件。网关先读懂它，执行转换规则，再写成供应商能接受的格式。为了不丢未知字段、签名和工具关系，它保留原文，对照原来的写法和修改后的写法；发出前还要检查真正的输出。

这些工作有用途，额外成本在做法：同一照片的字符串被多处反复读；每套一层文件夹，先把照片重新打印进这一层的 JSON；最后检查又复印了多层内容；比较两种 JSON 写法时，还可能先展开两棵完整对象树。

读过 4 GiB 的逻辑跨度，不等于分配 4 GiB。累计申请 120 MiB，也不等于同时占用 120 MiB；已释放的内存可以反复被下一步使用。优化必须分别看 CPU、累计分配、存活堆和进程工作集。

## CPU 实测：大图片忙于扫描，小事件忙在其他地方

| 场景 | 三次累计 CPU 样本 | `jsonStringEnd` 自身占比 | `scanRaw` 自身占比 |
|---|---|---|---|
| 2 MiB 图片＋工具历史 | 63.00／62.52／62.56 秒 | 38.68%～39.32% | 27.84%～29.08% |
| 31 MiB 图片＋工具历史 | 61.28／61.15／61.33 秒 | 40.55%～41.46% | 29.17%～29.26% |
| 约 2 MiB、1,800 文本块 | 63.81／62.59／62.67 秒 | 24.42%～24.83% | 19.98%～20.73% |
| 连续 512 个小增量 | 69.54／71.05／69.34 秒 | 0.76%～0.80% | 0.27%～0.37% |

每份采样窗口均为 60 秒，CPU 样本均大于 10 秒，无需延长。多线程累计 CPU 时间可以超过墙钟 60 秒。上述两列是 flat（函数自身），31 MiB 时合计约七成；不能改用含子函数的 cumulative 再相加。

CPU 表前三行使用 JSON 响应，最后一行使用 SSE。全图分母是整份网关样本；protocol 聚焦图会过滤调用链，不能把过滤后的比例直接当作全网关占比。

2 MiB 图中，`Compiled.EncodeRequest` 累计约 47.6%，其中原生保护约 26.4%～26.6%；默认规则的 `convertOwnedRequest` 约 7.1%～7.4%。这些调用子树有包含关系，也不能与分阶段墙钟时间直接换算。

小事件的 `CompiledConversion.Event` 累计约 16.17%～17.80%。图中较宽的 `runtime.cgocall` 主要通向 `WSASend → Flush → gatewayStream.emit`：首份 profile 有 10.94 秒样本在这条发送栈上。它不是数据库开销的证据。[系统调用明细](artifacts/conversion-flamegraphs-dev72/events-cgocall-traces.txt)保留了调用链。改变 flush 可能改变首字延迟、背压和取消，不能直接合并发送。

## 处理账本：一张图片到底经过几轮

以下为 31 MiB **base64 文本**，不是解码后图像大小。Anthropic 同协议、工具结果内含图片，模型改名。完全不改模型也出现基本相同的大载荷规模。

| 阶段 | `jsonStringEnd` 逻辑跨度 | `scanRaw` 输入规模 | 容器输出规模 | 资源计量结构访问 |
|---|---:|---:|---:|---:|
| 解码 | 1,116.005 MiB | 496.002 MiB | 31.000 MiB | 334 |
| 默认转换 | 558.007 MiB | 372.005 MiB | 0 | 2,581 |
| 编码及原生协调 | 2,418.011 MiB | 1,116.006 MiB | 496.003 MiB | 924 |

`jsonStringEnd` 总跨度约相当于 **132 个图片长度**；`scanRaw` 的字符串第二遍遍历约为另 **64 个图片长度**。这是实际计数器记录的逻辑跨度，不是硬件物理读取量，也不表示执行了 132 次根 JSON 解析。`scanRaw.input`、第二遍跨度和规范化输入有包含关系，不能全部累加。这份 31 MiB 账本尚未包含后来补加的最终线格式校验计数。

编码生成 22 个容器，其中 16 个带大载荷：

```text
媒体 source → 图片块 → 工具结果 content 数组 → 工具结果对象
            → 消息 content 数组 → 消息对象 → messages 数组 → 请求对象
```

**8 层 × 2 套投影 = 16 个大容器输出**。两套分别是当前语义投影和原生协调的基线投影，因此 31 MiB × 16 约等于 496 MiB。这是构造出的字符串总长度，不是堆峰值，未包含所有运行时分配。[容器调用栈](artifacts/conversion-flamegraphs-dev72/ledger-2MiB.json.containers.json)可核对每一层。

每条规则后的检查仍遍历容器，但大值缓存确实在工作：

| 2 MiB 样本规则 | 计量访问 | 规范化访问 | 大值计量命中 | 未缓存 `scanRaw` 输入 |
|---|---:|---:|---:|---:|
| `block-assistant-history` | 157 | 157 | 6 | 209 字节 |
| `client-stream-options` 等多数小字段规则 | 150 | 150 | 6 | 209 字节 |
| `text-tool-results` | 380 | 150 | 17 | 507 字节 |
| `request-signatures` | 387 | 157 | 17 | 507 字节 |

这次同协议请求执行 11 条请求规则，不代表本轮逐项测到了全部 31 条规则的所有分支。不能继续用旧实现“每条规则复制全文”的描述解释当前成本。

## 分配：内存具体申请在哪里

控制条件下的阶段定位，每项五次，中位数如下。每轮开始前主动 GC，计时段内无 profile；这不是完整 HTTP 正式结果。

| 负载 | 阶段 | 耗时 | 累计分配 |
|---|---|---:|---:|
| 2 MiB 图片／工具历史 | 解码 | 72.19 ms | 4.065 MiB |
| 同上 | 默认转换 | 45.49 ms | 0.0329 MiB，约 34 KiB |
| 同上 | 编码及协调 | 168.13 ms | 38.233 MiB |
| 约 2 MiB、1,800 块 | 解码 | 54.53 ms | 15.685 MiB |

完整 HTTP 的 2 MiB 分配 profile 补出以下热点：

| 分配位置／调用子树 | 采样分配 | 解释 |
|---|---:|---|
| `valueReader.fragment → strings.Clone` | 38.85 MiB | 多处片段复制，包含校验、媒体编码及续传提取 |

pprof 的 `MB/kB` 标签在此按二进制尺度换算，本报告统一写 MiB。该 profile 总采样约 140.56 MiB，其中约 11.99 MiB 属于 `writeHeapProto` 采集器子树。它用于找来源，正式累计分配以无 profile 结果为准，不能扣一个估计比例冒充精确请求值。

### 最终校验又复制了 26 MiB

[`builtin/wire_contract.go`](../backend/protocol/builtin/wire_contract.go) 的 `readWireObject` 使用公共复制读取方法。最终请求检查调用 `adapter.decodeRequest(value, EvaluationContext{})`，没有请求内共享读取上下文。为了检查工具关联，这条路径重建多层快照。

后补的 2 MiB 账本记录了 **39 次片段复制，长度合计 26.002 MiB**，另有约 2 MiB 容器输出。完整 HTTP 的 38.85 MiB 不能全部归到最终检查；媒体编码、续传载体提取和 `continuationSession` 也贡献复制。此前进度描述将总体数字贴在最终检查上，现按账本纠正。

检查的功能必须保留；可改的是读取方式。尤其用户 `after` 映射可以改变最终正文，不能拿此前的通过结论替代这里的检查。

### 原生比较仍有整树解码

[`native_reconcile.go`](../backend/protocol/native_reconcile.go) 的 `equalNativeValues` 已能快速处理原值相同、根小字段不同的情况。不确定时仍进入 [`value_schema.go`](../backend/protocol/value_schema.go) 的 `equalValues`，完整解码左右两树。

这项语义比较有必要：键顺序不同、`1` 与 `1.0`、转义拼写不同，不应直接视为用户改写。优化方向是逐层借用子值比较，不能直接用字节不等代替语义不等。

## 正式完整 HTTP 结果

**方法校正：**第一组 `final-measure-*` 在计时前调用旧 `reset`，会主动 GC 两次，影响起始堆状态，仅保留为诊断对照。正式 `timing-measure-*` 使用 `reset-without-gc`，保持自然 GC 历史，无 profile、精细计数或主动 GC；两组不混合求中位数。

每格的两个数依次为 **JSON／SSE**。除明确列出外，关闭正文日志、单候选；所有值为五次中位数，MiB 使用 1,048,576 字节。

原始记录中的 `SizeMiB` 是夹具参数，只有图片／多节点夹具使用它；小请求和小事件的输入正文约 1 KiB 文本，协议矩阵使用 short／tools32 夹具，不能把这些记录也解释成 2 MiB 请求。

|---|---:|---:|---:|
| 2 MiB，1 并发 | 391.16／389.88 | 122.72／122.87 | 35.69／35.74 |
| 8 MiB，1 并发 | 1,573.74／1,543.62 | 486.63／486.78 | 176.98／169.13 |

| 2 MiB，4 并发 | 580.84／572.13 | 490.71／491.32 | 135.25／120.80 |
| 小请求，1 并发 | 3.77／4.24 | 1.72／1.89 | 5.82／4.98 |
| 小请求，4 并发 | 11.08／10.62 | 6.89／7.54 | 5.82／5.33 |

例如 2 MiB 四并发 SSE 的五次峰值范围为 **90.75～133.93 MiB**，中位数 120.80 MiB；单个峰值不能当成稳定常量。全部逐次堆峰值和工作集均保存在 summary 及各场景 measurements.json 中。

从 2 MiB 到 8 MiB，输入增大四倍，耗时和累计分配也约四倍；这一段未观察到明显超线性放大，但不能据此外推 31 MiB 或四并发大负载。

并发表的耗时是整批完成耗时，分配是整批分配，不是单请求 P95/P99。只有五次样本，不发布高分位数。每批完整消费响应并检查生成次数；图册中的 20 毫秒峰值是采样值，小请求可能在两次采样间完成，不能视为连续精确峰值。

耗时截止到客户端完整消费；分配和峰值读取在日志排空后。本地工具通过停止／重启日志写入器排空队列，所以分配还包含该测试辅助过程，尤其比较小请求时不能当作纯协议函数分配。所有逐次测量保留相同口径；下一批配对也必须保持一致或同时重测两边。

旧 GC 对照的 2 MiB JSON 中位耗时 426.19 ms、分配 122.74 MiB、堆峰值 35.55 MiB，不能与正式自然 GC 峰值混用。候选数增加带来更多预检和分配，真正上游命中仍为一次；首候选编码复用并没有取消其他候选的资格检查。

正文日志旧组工作集从约 111 MiB 上升到后续约 184 MiB，而 Go 堆没有同步单调增长。可能涉及数据库和运行时保留，当前证据不足以判为泄漏或排除泄漏，需另做长时排空后的系统内存调查。

## 活跃对象、释放与微基准

`heap-active` 在请求开始约 250 毫秒时请求快照，不是峰值触发器：2 MiB 图片可能尚在处理，小事件通常已结束。堆 profile 还可能滞后若干 GC 周期。

图片样本该快照约 13.17 MiB，可见解码媒体、容器和路由准备分配；日志排空并诊断性地 GC 两次后约 6.53 MiB，主要为进程基础设施，未再采到大载荷。它支持临时副本可回收，不证明所有长时路径无增长。

阶段保留实验刻意让 body、request、wire 存活至编码结束，再清除变量。`retention.json` 的 Heap 在该阶段主动 GC **之前**读取，不能当作回收后保留量；应看对应 `.pprof`。图册用 FORCED GC / RETAINED OBJECTS 标注。对象分配位置、代码生命周期和释放结果一起用于归因，不仅凭堆图断言引用关系。

局部扫描原型五次中位数：2 MiB 字符串从 **3.518 ms → 2.187 ms**，约减少 **37.8%**，两者零分配。10 秒 fuzz 共 **275,548 次**，未发现局部等价失败。这里只验证合法字符串 token 计量，没有证明整个资源检查、错误顺序和取消行为等价，原型没有接入生产，不能宣称 HTTP 快 37.8%。

缓存命中：2 MiB `Value` 约 26.15 微秒，小值约 10.5 纳秒。长键确有成本，但远小于数毫秒扫描，不优先改公共 Value 表示或增加全文摘要。

通用边界实验覆盖 16 协议组合 × 4 种边界 × 5 次，每次 10 个约 24 KiB 请求。Anthropic 同协议折合每次：typed 约 **2.88 ms／0.992 MiB**，`set-same` **9.64 ms／5.173 MiB**，`set-changed` **9.22 ms／5.212 MiB**，JSON 条件 **9.52 ms／5.260 MiB**。这是顺序定位实验，不是交替版本验收。规则必须观察前序修改，JSON 边界也有规范化作用，因此 set 相同值不等于可以删掉同步。

正式矩阵有 6 个环境阻塞项：16／31 MiB 单并发、8／31 MiB 四并发、31 MiB 正文日志／媒体外置。启动检查时剩余承诺额度约 1.45～1.82 GiB；31 MiB 四并发要求的 **16 GiB 承诺额度＋12 GiB 物理可用**没有降低。31 MiB CPU 早先在允许单并发的环境下采齐，不能替代后来被阻塞的正式峰值和耗时。

早期所有小负载统一要求 2 GiB 承诺额度，造成不必要阻塞；在已测 2 MiB 峰值证据支持下，诊断工具将小负载门槛分别设为 1 GiB／小文本 0.5 GiB。大负载门槛未改；预检失败或无法取得内存状态时仍阻止启动。修改过程与阻塞记录均保留。

历史约 370 毫秒 profile 来自 `a8341c2` 的 codec 测试进程，明确标为历史定位样本，不用于当前正式结论。

HTTP 矩阵覆盖 16 个源／目标协议组合 JSON/SSE，另有 Chat→四目标工具定义请求。工具定义成功不等于完整生成工具调用、执行工具、第二轮续传已跑过本轮性能矩阵。

初期矩阵失败来自新夹具：复合帧误用单事件解码、模拟响应缺少 created/model/message ID、Chat 未请求流 usage、为目标附加了不支持的字段。修正的是夹具，生产验证没有放宽。另有边界测试选择器错误；失败日志保留，不把夹具故障当成真实渠道问题。

系统剩余承诺额度与空闲物理内存不同：它表示系统还能为程序承诺多少内存支持。即使还有十几 GiB 空闲物理内存，也可能已接近承诺上限。本轮没有关闭用户进程、修改页面文件或降四并发代替验收。

启动预检保存的是 Windows `FreeVirtualMemory` 读数；最终另以性能计数器 `CommitLimit - CommittedBytes` 核对，约为 1.82 GiB，与大负载阻塞判断一致。采样只说明启动当时的环境，不保证整轮其他进程的占用不变。
