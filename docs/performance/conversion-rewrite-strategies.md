# 协议转换：三种重写策略

状态：提议，可直接实施。编写于 2026-11-17。测量基线：`fabb0bf8`（即本分支加上 golden 语料提交，该提交不包含在本 PR 中）。

本文取代 `phase-1-and-4-runbook.md` 与 `phase-3-generated-executor.md` 中的渐进式计划，作为
性能工作的方向。这两份文档保留，用于其测量数据和"不要尝试"的结论。

任一策略的验收标准：在交接文档的八个场景上，相对上游 `deploy`（即 dev.173 的生产代码），
**吞吐提升 ≥ 4 倍，或峰值内存降低 ≥ 2 倍**，且转换输出与当前解释器逐字节一致。

## 1. 现状

### 1.1 已尝试的方案及放弃原因

第二轮（`2f1afba5` .. `d83433c5`，未合并）把语义文档改为基于 arena、带 epoch 标记、写时复制的
`Node`，并在其上加入 epoch 证明以跳过 verdict 比较（4.1）和帧摘要（4.2）。端到端相对 dev.173
的结果为 **0.86×–1.11×**，低于其起点 `fabb0bf8`，且每个请求多出约 380–490 次分配。4.1 和 4.2
对整条流水线没有可测量的效果。该工作已放弃；本分支从第一轮工作重新开始。

结构性的教训：所有权证明、epoch、侧表和写时复制，每加一层都是在给一条本已被通用解释执行和
重复遍历主导成本的流水线增加工作。让通用树的复制和比较变便宜，并不能消除这些复制和比较。

### 1.3 `fabb0bf8` 的时间花在哪里

CPU profile（`--mode=profile`，15 秒）分为三部分：

| 场景 | 调度器唤醒（`runtime.semawakeup`） | 请求处理（`serveProtocolRequest`） | Socket 写入（`syscall`） |
|---|---:|---:|---:|
| `chat-short` | 65.5% | 5.5% | 13.3% |
| `chat-anthropic` | 58.6% | 8.0% | 13.5% |
| `tools32` | 49.8% | 28.0% | 5.9% |
| `history256k` | 13.3% | 51.6% | 3.9% |
| `image2` | 7.1% | 54.8% | 2.7% |
| `stream256-cross`（syscall 另含 `stream256`） | 1.3% | 84.6% | 79.6% / 83.5% |

三个独立的问题：

1. **小请求：瓶颈是 goroutine 交接，不是转换。** 约 60% 的 CPU 在
   `wakep → startm → semawakeup → pthread_cond_signal`，由 `ready`（36%）和 `newproc`（28%）
   触发。profile 没有把这些唤醒归因到具体调用点；需要审查的每请求 goroutine 和定时器包括 Hertz
   连接、`net/http` 客户端 `persistConn` 读写循环、截止时间定时器和用量写入器。这里转换只占约 5% 的 CPU。单靠重写转换，这些场景到不了 4 倍。
2. **大请求：解释器和重复遍历。** `history256k` 中，输出计划解释器
   （`compiledOutputPlan.build`）占 33%；`EncodeRequestValue` 18%，`ValidateRequestOutput`
   10%，`preserveMappedNative` 10%，`CompiledConversion.Request` 8%。`image2` 中，重复扫描
   同一批字节占主导：`IndexByteString` 17%，sonic `skip_one` 24%，`CountString` 11%，
   `utf8.ValidString` 5%。`history256k` 的分配量是请求体的 31 倍（每个 256 KiB 请求分配
   7.9 MiB），`image2` 是 8.3 倍。
3. **流式：每帧一次 flush。** 流式场景 80–84% 的 CPU 是 `responseStream.Flush`
   （`server/gateway_stream.go:169`）里的 socket 写入，自 dev.173 以来未变。

内存：请求结束后存活堆约 44–53 MiB，其中 44.5 MiB 是编译后的协议包（`CompilePreset` →
表达式树、输出计划、解析后的 `Value`、JSON schema）。四个内置 `mapping.json` 源文件共
5.85 MB（1.7.0 的四个定义共 0.49 MB）。负载开始后前两秒内峰值 RSS 从约 75 MiB 涨到约
330–360 MiB，之后不再回落，因此峰值 RSS 由每个请求的分配量决定，而不是由存活数据决定。

## 2. 策略 A —— 用寄存器字节码虚拟机替换计划树（推荐）

**观点：** 应该做的就是这个。输出计划和表达式树是一个通用树解释器，外面包了计划节点、操作数
数组、计量器和重复校验。把它们换成扁平的、带类型的字节码，由一个紧凑的循环执行。保留 DSL 和
Spec/Mapping 格式；只改变编译器产出什么、以及由什么来执行。

### 设计

- **编译**：每个 Mapping 程序（`decode_*`、`encode_*`）在激活时编译一次，得到带常量池和固定
  寄存器文件的 `[]Instr`。指令是定长结构体（`op uint8, a, b, c uint16, k uint32`），不是接口
  或闭包。
- **寄存器保存借用的 `Value` 字节区间**，不复制。`read` 变为按路径偏移缓存的指针查找；
  `literal` 变为常量池加载；`object`/`array` 直接写入同一个输出缓冲区。
- **把各个遍历融合进程序。** 资源计量（`Nodes`、`BufferBytes`）、步数限制和输出校验，变成
  编译器在输出点插入的计数和检查，而不是单独的遍历。`ValidateRequestOutput` 由"只产出符合
  schema 的结构"加"内联检查剩余的运行时约束"替代。
- **尽量直接解码到目标编码器。** 同协议和保留原生数据的路径上，程序把未改变的字节区间直接从
  输入复制到输出（一条"复制区间"指令）。这顺带消除了 `preserveMappedNative` 里的第二次编码：
  不再有需要重建并比较的基线。
- **读集合在编译期已知。** 每个程序记录它读取的 Core 路径。runbook §4.4 中的"读集合分析"
  变成字节码本身的属性，而不是单独的证明。
- **错误保持精确路径和顺序。** 每条可能失败的指令携带源路径索引；首个错误的顺序跟随指令顺序，
  而指令顺序跟随当前的求值顺序。
- **保留树解释器作为对照**，放在 build tag 后面，直到语料和差分测试全部通过，再删除。

### 预期效果

未测量。选择它的依据：`history256k` 中仅输出计划解释器就占 33% 的采样，编码、重新校验、原生保留
和转换入口的累计占比分别为 18%、10%、10% 和 8%（与解释器的占比有重叠）；`image2` 中字节
重复扫描约占扁平采样的 57%。对输入只做一次前向遍历、用区间复制，可以去掉其中大部分。
对小请求帮助不大（见 §1.3），所以要与策略 C 配合。

内存：44.5 MiB 的编译包变为紧凑的指令数组和常量池。每个请求的分配应降到大约"输出缓冲区加一个
寄存器文件"，这正是降低峰值 RSS 的途径。

### 步骤

1. 为一个程序做原型：openai-chat 的 `encode_request`。以
   `BenchmarkRequestMemoryPipeline/openai-chat` 和 `history256k` 与解释器对比。
   **停止条件：** `history256k` CPU 提升低于 3 倍时，停下并报告，再决定是否继续。
2. 覆盖四个内置包用到的所有操作；对语料与解释器做差分运行。
3. 把计量、步数限制和输出校验移入指令流。
4. 加入区间复制指令，删除 `preserveMappedNative` 的第二次编码。
5. 切换默认执行路径；解释器在 build tag 后保留一个版本。

### 风险

编译器缺陷表现为无声的语义差异。只有与当前解释器的差分运行（覆盖所有 mapping 样例、全部跨协议组合、流式、错误和限制边界
用例）能防住，
所以对照实现要保留到两者都通过。自定义用户包必须能在运行时、无 Go 工具链的情况下编译成同样
的字节码，本设计满足这一点（不生成 Go 代码）。

## 3. 策略 B —— 字节级转码器，不构建语义文档

**观点：** 最激进的选项，也是唯一有可能在大负载上逼近上限的选项；同时风险最高。只在策略 A 的
原型表明剩余成本来自语义文档本身、而非解释器的路径上采用。

### 设计

- 热路径上不再构建中间的 Core2 文档。每个 Mapping 编译为一个**流式转码器**：一个状态机，对源
  JSON 只做一次分词，直接写出目标 JSON；未改变的区间（消息文本、base64 图片数据、工具参数）
  直接复制，不解码也不重新编码。
- Core2 保留为**规范**和语料对照：A→B 的转码器必须产出与 A → Core2 → B 相同的字节。冷路径
  （校验、Agent、管理）仍然构建语义文档，那里速度不重要。
- 流式帧对每帧使用同一个转码器，并为关联关系和工具调用索引保存每个流的状态。

### 预期效果

未测量。依据：`image2` 分配量是请求体的 8.3 倍，且大部分 CPU 花在重复扫描字节上；
`history256k` 是 31 倍。区间复制转码器对每个输入字节大约只处理一次，大约只分配一个输出缓冲区。
这种形态才可能在大请求上达到内存降低 ≥ 2 倍、吞吐 ≥ 4 倍。

### 风险

最高。缺失/null/零值、顺序、工具关联、源协议拥有的扩展，目前都由共享文档保证。转码器必须
针对每一对协议重新保证所有这些。跨协议组合为 N×(N−1)；四个内置协议就是 12 个转码器，不过它们
由 Mapping 生成，而不是手写。

## 4. 策略 C —— 网关并发与流式写入路径

**观点：** 无论选 A 还是 B 都必须做，因为小请求的成本不在转换上。没有 C，任何转换重写都无法
让 `chat-short`、`burst4` 或 `chat-anthropic` 达到 4 倍。

### 设计

- **减少每个请求的 goroutine 交接。** Profile 显示小请求约 60% 的 CPU 在调度器唤醒上。逐一审查
  每个请求相关的 goroutine 和定时器：出站 `net/http` 客户端的 `persistConn` 读写循环、每个请求
  创建的 `context.WithDeadline` 定时器（`relay.dynamicTimeoutClient.Do` → `setRequestCancel`）、
  用量批量写入器的唤醒、Hertz 连接处理。用一个截止时间轮替代每个请求的定时器；在传输层允许的
  情况下，在请求 goroutine 上直接完成上游交互；用量持久化按数量和时间批量处理，而不是每个请求
  唤醒一次。
- **合并流式 flush。** 对上游已就绪的一批帧只 flush 一次，并且在阻塞等待下一次上游读取之前
  一定 flush；不使用定时器，所以没有帧会被延迟。`CommitDelivery` 随 flush 一起移动，绝不报告
  尚未 flush 的字节。目标是流式场景 80–84% 的 syscall 占比。
- **用量持久化移出热路径。** SQLite `SaveUsageBatch` 占 `chat-short` 的 2.4%；改为每 N 个请求
  批量执行一次。

### 预期效果

未测量。调度器占比（小请求 CPU 的 49–66%）就是 C 在这些场景上能找回的上限；流式收益取决于每次
上游读取到达多少帧。

### 风险

低到中等。流式批量改变的是写入时机，不是内容；晚期失败和空闲超时的约定需要重新测试。去掉
goroutine 不能破坏取消和浏览器断开的语义。

## 5. 建议与顺序

1. **先做 C**（最小、独立、能解锁小请求的收益），单独测量。
2. **再做 A**，从 openai-chat `encode_request` 原型开始，带 3 倍停止条件。
3. **B** 只用于大请求路径，且仅当 A 的原型表明语义文档是剩余成本时才做。

每一步的门槛：差分运行中输出与解释器逐字节一致；完整非 race 测试通过且在五分钟内；每个场景相对 dev.173
的数字单独报告；没测的就写"未测量"。不得削弱断言、放大限制或删除样例。

## 6. 测试耗时

在 `fabb0bf8` 上，完整非 race 测试已经满足五分钟限制（236.7 秒；server 230.4 秒），这来自
§1.2 列出的两份 Agent Note 中记录的分级与 server 分片。进一步缩短应与策略 A 一起做：server 包
大部分时间花在测试夹具里编译和校验内置协议包上，一个紧凑的、在夹具之间共享的字节码编译缓存会
直接缩短这部分时间。
