# 交接文档：第 3 阶段——生成执行器

Status: idea-stage, deliberately not a runbook. Written 2026-11-16.

本文档是方向，不是指令。第 3 阶段是项目中最庞大、最不确定的改动；今天把它写成固定序列，
等于假装拥有我们尚未赚得的信心。以下是这件事的形状、值得尝试的想法、会阻碍它们的东西，
以及在写下任何代码之前必须回答的问题。

前置条件：第 1、4 阶段已落地并完成测量。在指针密集的文档之上做第 3 阶段，只会产出仍在
十几次遍历中追逐指针的生成代码——收益只在这一顺序下复合。

---

## 一句话概括

当前运行时每请求解释一棵 `compiledOutputPlan` 树。第 3 阶段改为：每个编译后的 Mapping
生成一次直筒式 Go 代码，之后每请求调用它。

类比是正则引擎：解释器每次匹配走一遍节点树；编译器每个 pattern 生成一个匹配函数。同一种
语言、同一套语义，常数因子与失败模式截然不同。

## 为什么它是唯一可能达到目标的步骤

实测而非假设：解释器分发为 2.74%（`buildNode`）+ 1.90%（`buildOperation`）的 flat 占比，
其中字符串 switch 约 1.5ns，因为 Go 已把它编译为按长度分桶的跳转表。仅移除 switch 只能
回收 1–2%。因此这里的论点**不是**「解释慢在 switch 上」。

论点是：逐节点解释强制了编译器无法优化掉的选择：

- 每个节点边界都要付出一次函数调用、函数序言、`advance()` 步数检查、错误装箱路径，以及
  结果结构体返回——即使是 `literal` 这种常量。
- 树的形状只有运行期才知道，因此编译器无法内联子节点、让值留在寄存器、融合相邻读取，或
  证明某棵子树零分配。
- 操作数被构建进通用的 `[]plannedOutput` 数组再重新检查，而不是以生成期即确定类型的具名
  局部变量存在。

生成代码可以做到以上全部。它**是否真的做到**，是本文档在没有原型的情况下无法回答的开放
问题。

## 形状：生成什么

每个 Mapping 的每个程序各一个函数：`encode_request`、`encode_response`、`encode_event`。
在当前位置编译计划时生成，以同一 revision 身份缓存，因此激活、校验与热重载语义不发生位移。

函数签名贴近当前入口——接收语义文档与每请求求值状态，返回计划输出或错误。变的是函数体：
没有树、没有分发、没有通用操作数数组。

保留解释器。它是参考实现、差分测试的 oracle，也是生成器拒绝处理某些程序时的回退。删除它
是后续基于证据的决定，而不是设计的前提。

## 值得尝试的想法，大致按「单位风险的期望收益」排序

**1. 生成期常量折叠。** `literal` 节点、静态可解析的指针、无条件选中的分支，都能折叠为
常量或直接访问。这一条几乎没有语义风险，很可能是最便宜的收益。

**2. 用具名局部变量取代操作数数组。** `buildOperands` 目前物化 `[]plannedOutput`（4 槽
栈数组，溢出则堆分配）再重新检查。生成代码可把每个操作数放在有类型的局部变量里，这也顺带
消除了我们已在 `buildIterationOutput` 修掉的逃逸，以及仍然存在的
`make([]JSONOutput, len(values))` 分配。

**3. 对静态已知指针直接访问结构体字段。** plan 已在编译期解析指针，`expression.pointer`
是静态的。生成函数可以直接读 `request.Content[2].Payload`，而不必每请求走一次指针路径。

**4. 父子融合。** `object` 带 `read` 子节点、`array` 带 `map` 体——这些正是 12 次遍历的
来源形状。生成代码可以把子节点内联进父节点的循环，而解释器在结构上做不到。

**5. 把计量并入遍历。** 字节／节点计数今天是独立遍历。生成函数可以边遍历边累加——与第 4
阶段的纪元是同一思路，但以结构方式实现，而非缓存一次比较结果。

**6. 生成期按文档形状特化。** 若 Mapping 结构可证明某程序只读 `Content` 与 `Tools`，生成
代码可完全跳过文档其余部分，而不是走一遍通用访问器。

## 困难之处，直说

解释器**通用地**完成的一切，都必须**按程序分别**复现：

- 每条错误消息及其精确 `path`，并保持首错顺序。
- 所有资源限制检查及其上报数值（`Nodes`、`BufferBytes`、`walkNodes`）——包括触发的先后。
- `advance()` 步数限制。
- absent／null／zero 的区别，以及字段顺序。
- `Value` 原始字节的保留，包括 span identity 缓存。

这就是全部风险所在。生成器的缺陷会表现为静默的语义差异，而不是编译错误。没有任何类型系统
会告诉你「你的生成编码器现在丢了一个 absent 字段」。只有语料能捕获它。

## 写代码前必须回答的开放问题

1. **在构建期生成，还是在包激活期生成？** 构建期生成意味着随程序发布的包有现成代码，但
   用户自定义包需要运行期编译器——而 Spec/Mapping 格式的全部意义就是用户无需 Go 工具链即可
   编写包。这很可能迫使采用激活期生成，从而让生成器成为运行期依赖，并改变启动开销的故事。
   先定这一点；它支配整个设计。
2. **每包生成代码的体积与启动代价是多少？** 大约一百个算子、四个包、每个若干程序。生成源
   是被编译成二进制，还是这其实是一个带扁平程序的专用解释器？答案决定这件事到底还算不算
   代码生成。
3. **差分测试如何在生产中而不仅在测试中工作？** 在 CI 中保留解释器作为 oracle 很容易。采样
   的生产比对是否有价值，代价是什么？
4. **生成器拒绝某个程序时怎么办？** 每个用到生成器不支持算子的 Mapping 都需要一个定义明确
   的回退，且该回退必须被测试；否则「部分程序变快」这一性质就会退化为「部分程序行为不同」。
5. **收益是真的吗？** 先为一个算子族做原型——`object` 带 `read` 子节点，这是最常见的形状
   ——并在承诺其余部分之前与解释器对比测量。若该原型显示不出有意义的倍数增长，就停下并如实
   报告；第 1、4 阶段本就已是正确的投资。

第 5 个问题最重要。先做原型，再考虑进一步设计。

## 值得与之一并权衡的替代方案

**把程序扁平化，而不是生成 Go。** 把 plan 树编译为带预计算操作数槽位的扁平指令数组。消除
树遍历与大部分分发，完全不涉及代码生成，保持单一运行期实现，并彻底避开「生成代码是第二套
语义」的问题。上限较低，风险小得多。若第 1 阶段的 arena 让遍历变便宜，这可能已捕获剩余收益
的大部分。

**只特化热点算子。** `object`、`read`、`array`／`map` 与 `literal` 很可能占节点的大多数。
在解释器内部为这些算子手写快路径，工作量只是生成器的一小部分，且不需要生成器。

**不动解释，专攻遍历。** 第 1、4 阶段已在针对这些遍历。若它们交付良好，剩余的解释器开销
可能并不值得一次重写。

诚实的预期：就我们已有的测量，「扁平化」与「特化热点算子」是最可能以第 3 阶段一部分风险
拿到大部分收益的两个选项。只有当第 5 个问题的原型显示出相对两者的大幅领先时，第 3 阶段
才值得尝试。

## 若推进，验收门

- 全部用例语料逐字节不变，包括错误路径与问题顺序。
- 对全部语料与生成输入扫描集，与解释器做差分运行。
- 解释器保持在 build tag 或配置开关之后可达，直到语料与生产观察期双双通过。
- 逐场景报告实测改善，不聚合。
- 任何场景不得回退；以一个用例换另一个用例的阶段并不算成功。

## 未承诺的事项

没有吞吐量投影。本文档背后的唯一实测数字是分发占比（flat 2.74% / 1.90%）、单节点代价
（5.8–8.3 ns）、调用量（短请求约 1,400 次，`history256k` 约 40,000 次），以及第二回合的
A/B 结果。代码生成能否达到 4x–13x 未知且未建模；第 5 个问题的原型正是为了在昂贵承诺之前
便宜地回答它。
