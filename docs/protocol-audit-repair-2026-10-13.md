| 错误详情 | 新增 response/event 的 error_metadata 规则。空 param 规范化；兼容模式把目标无法结构化表达的字符串细分码／参数附于消息，严格模式拒绝结构损失。未知对象及扩展继续保护。 |

| 审计工具 | 主失败与次级问题分开；实际客户端 HTTP、可观测上游 HTTP、逻辑状态分开；HTTP 200 SSE 限流仍失败。生成失败后停止正文／工具服从断言。官方与 Vercel SDK 独立调度。 |

规则按实际内置模块启用；复用模块的自定义定义获得修复，手写编码器不会

### 失败主因与责任边界

以下按原始证据人工归类，73 项互不重复。报告的通用
failureCategory 有时只能标为待调查或 SDK 消费失败，不能把这些
标签直接解释为 SDK 或网关实现缺陷。

| 主因 | 项数 | 证据及边界 |
| --- | ---: | --- |
| HTTP 524 | 30 | 7 项直连、23 项网关链路；Cloudflare 返回 origin_response_timeout。并发 1 的成对测试也出现，不能仅归因于本轮并发 32。 |
| 上游流空闲超时 | 18 | 网关等待不到新上游数据；能确认停在上游读取阶段，不能只凭超时确定是供应商、渠道代理还是网络链路。 |
| 非标准 `***.failed` | 10 | 载荷明确 upstream_error，但事件名违反 Responses 契约；网关保留主因并拒绝 /type，不能改写为成功。 |
| 渠道 `new_api_error` | 7 | 内层 get_channel_failed／do_request_failed 表示渠道失败；尚无具名类型映射，伴随 unsupported_capability 次级诊断。属于渠道原始故障与网关适配边界并存。 |
| HTTP 200 SSE 内限流 | 2 | 直连也捕获到；按真实限流失败计入，不因 HTTP 200 算成功。 |
| 直连 Chat upstream_error | 2 | 请求未经过网关，渠道直接返回失败。 |
| unexpected EOF | 1 | 连接提前结束。 |
| 流内 ID 改变 | 1 | 原始上游既有 ID 变化；网关在投影前按 /id 拒绝，保留源归属。 |
| socket timeout | 1 | 连接超时；本项不与流空闲超时合并。 |
| marker 未遵循 | 1 | 系统要求已送达上游，回答未包含测试 marker。 |

18 项空闲超时均没有可观测的 upstreamHttpStatus。代码会在 transport
交付 HTTP 响应后立即记录状态；本轮这些请求停在响应交付之前。
同一个空闲计时器保护等待响应头与读取流正文两种阶段，所以错误名
带有 stream 不代表上游已经开始发送正文。计时器不计算网关消费处理
数据的时间，默认空闲上限为 120 秒，不能与脚本的 180 秒总超时混淆。

因此，73 项失败不能写成 73 个独立网关 bug。本轮剩余失败主要反映
渠道可用性、链路中断及渠道输出契约问题。`new_api_error` 的次级
转换诊断仍是明确的适配边界；未知厂商类型没有被整体放行。
Cloudflare 非 OpenAI 格式错误体的部分字段诊断仍较笼统，属于可改进
的故障定位，不应据此把 524 解释为生成转换失败。
本轮独立执行了更多 SDK 子用例，渠道可用性也不同，因此不能用与
上一轮总通过率的简单比较证明转换回归或修复收益。

以下记录可定位代表性失败，路径相对于本轮完整审计目录；它们仅供
本地核查，向渠道分享前仍需脱敏审阅。

## 待渠道核查的脱敏问题单

仅保存在项目中，不自动向渠道发送数据：

1. Responses 失败事件名应为 response.failed；原审计及本轮实测均出现
   `***.failed`。保留内层错误类型以区分并发限制和上游不可用。
2. 同一 Chat 流中的既有 id 不应改变；原报告已捕获 resp- 与 resp_
   不同 ID。网关仍拒绝，不以覆盖身份修复。
3. Responses response.created 应携带必需字段；原报告直连存在
   model/created_at 缺失后才出现。本轮不将后出现描述为已建立值改变。
4. 原工具请求为 Chat 的嵌套 function.name 结构，却收到缺少
   tool_choice.name 的报错。本轮成对请求成功，不能断言渠道内部原因已解决；
   应结合各次路由及模型核查。网关不改成 Responses 的扁平格式。
5. 本轮大量 524、上游流空闲及 new_api_error，需核查渠道路由、
   账号并发和源站可用性；并发 1 也有直连 524。先恢复渠道稳定性，
   再用同一请求做成对验证，避免继续付费重跑得到相同可用性噪声。

特殊媒体、服务端工具、完整 Responses 历史恢复及供应商真实签名接受范围，
不因文本与标准函数工具通过而扩大声明。
