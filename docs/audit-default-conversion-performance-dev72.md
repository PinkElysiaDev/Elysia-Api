# 默认转换规则性能优化验收记录（dev.72）

> 历史验收记录：旧转换实现、baseline/optimized 对照入口及一次性资源 profile 已在[测试裁剪](backend-test-review.md)中移除。下文命令及结果对应原提交。

本轮目标是保留转换规则、逐规则预算、来源及最终校验，消除连续内置规则对整个语义文档的反复 JSON 往返。未删除原生快照，未截断历史，未关闭默认规则。仅本地提交和模拟上游验收，没有推送或调用收费渠道。

基线为 `e376367`，运行时代码截止 `f119ded`，工程检查代码提交为 `f0d39bf`；编译器仍为 `2.0.0-dev.72`。`da681ef` 之后仅补充测试、测试常量与源码快照清单，运行时代码相同；文档提交不改变已测运行时代码。

核心运行时优化已落地，本地工程回归通过，转换阶段的耗时/分配/采样堆目标达到。完整链路内存问题尚未解决，补充并发性能验收因一次旧版 OOM 未全部完成；下面分别列出成功、失败和未覆盖范围，不将本轮标记为所有性能及真实环境验收完成。

## 变更与等价性约束

1. `conversionState` 为一次阶段执行持有独立对象。内置请求、响应、事件动作共用对象；JSON 路径条件与通用 set/remove/transform 同步当前 JSON，后续动作看到前序修改。阶段间与事件间不共享可变状态，不在失败后重跑规则。
2. 常规请求采用独立可变容器，`Value` 的不可变字符串共享。含 ingress 或依赖 JSON 的自定义策略预先选择原入口/出口边界，不通过事后失败回退。用户输入、其他候选和并发调用不被修改。
3. 逐规则检查仍执行。缓存只减少不可变值的扫描；同一值出现多次仍重复计数。缓存条数和引用内容长度有界，满时回到扫描，疑似超限时走原计量器保持第一处错误和数量。
4. 节点先做种类及匹配判断；无 JSON 条件的内置动作直接处理字段。签名恢复没有候选或资源键已经命中时避免全文摘要，需要时一次节点执行只计算一次摘要。
5. 固定选项复用现有编译动作目录。匹配前不提前抛出选项错误，覆盖后的值与类型仍验证。工具字符串包装只处理目标 payload，转义形式保留旧解码再编码语义。
6. 空集合省略、转义、无效 UTF-8 字符串与键碰撞的规范化继续模拟旧编码边界；不能用“业务没修改”跳过旧边界本来会发生的表示变化。

默认规则覆盖目录：请求 14、响应 8、事件 8、源事件 1，共 31 个稳定 ID。`chat-stream-identity` 状态机本轮没有修改，其完整流回归继续保留。

## 测量口径

Windows amd64、Ryzen 5 7600X（6 核/12 线程）、Go 1.26.5、Node 24.18.0；`GOGC=100`、`GOMEMLIMIT=8GiB`。8 GiB 是 Go GC 软目标，不是进程硬上限。图片大小指 base64 文本字节数；31 MiB 不是解码后的图片大小。

转换、HTTP 及微基准场景完成五组配对，交替旧/新顺序；补充完整编解码并发测量因旧版 OOM 未完成五组，单独列出，不纳入完整通过。小请求、响应、事件与实际修改分支也按 mode 分开启动进程并交替顺序。正式计时没有开启逐规则日志或 CPU profile；profile 另行运行。性能测量不与本轮全量测试、构建和 race 并行。

转换阶段输入预先解码，每个并发 worker 拥有各自输入。累计分配统计转换新增分配，采样堆峰值包含已经存活的输入。HTTP 的客户端、网关、供应商分别运行在不同进程，内存只采网关。累计分配、存活堆、20 ms 采样堆峰值和 Windows 工作集分别记录；工作集包含 Go 堆之外的进程内存。

旧执行器测试基准保留于 `conversion_baseline_test.go`，HTTP 旧版本使用从 `e376367` 导出的源码，只加入相同的测试进程控制代码。未用“隔离业务”数据替代完整规则成绩。大样本转换本身只有少量语义节点；约 1,800 小节点、历史重组、工具对象包装与签名恢复通过补充工作负载单独测量。

HTTP 初测发现旧归档和工作区的内嵌资产不同，正式数据重新使用相同前端与源码查看器资产构建两个版本。这些资产不参与本测试的请求处理，但对齐它们可以排除进程映像工作集差异。每组均先 JSON 后 SSE，网关在二者之间回收堆；SSE 工作集可能包含同一进程之前使用的页面，不能把它解释为纯 SSE 堆需求。

## 过程异常与剩余范围

早期共享 ApplyValue 状态的版本虽然减少耗时与累计分配，却没有达到堆峰值目标；随后增加常规 Request 在入口/出口直接保留 typed 对象，才取得最终数据。早期成绩不计入最终结果。

第一次长批次在进入 31 MiB 四并发时中断。Windows Application 事件确认崩溃的是 PowerShell 宿主（`0xc00000fd`），没有 Go 断言失败证据。换用 Python 直接启动子进程并写日志，分别补跑缺失的 31 MiB 四并发及 2 MiB 32 并发；中断段不作为通过。

首轮固定版本 staticcheck 在既有 `relay/proxy_tunnel_test.go` 发现裸数字 HTTP 502（ST1013）。单独提交改用 `http.StatusBadGateway`，相关代理隧道回归通过。为了在同一提交重做最终工程检查，主动中止旧提交尚未完成的 Go/race 批次；这些记录归档在 `before-test-constant-fix`，不计入最终通过。

最终补充的完整编解码四并发旧版运行另有一次真实 OOM，与前述 PowerShell 宿主异常不是同一个问题。日志、退出码及失败后系统内存数据均保留；其余补充运行没有继续启动。此项性能验收保持未完成，不因工程测试全部通过而关闭。

本批没有改变六份大载荷表示的所有权、编解码模块进入 typed 快速路径的条件、候选预编码与实际发送重复编码、原生协调、正文日志脱敏。完整 HTTP 仍有显著分配与等待，不能把转换阶段的低新增分配解释为整个网关只占几十 KiB，也不能把采样堆下降外推为工作集同等下降。

第一版保留逐规则的完整结构计量及规范化，没有为所有字段增加细粒度变更区域追踪；这保证中间表示与旧 JSON 边界一致，也解释了节点密集场景仍有遍历和容器开销。共享段和有界 Value 缓存解决的是重复全文编解码，并不承诺所有无操作规则都达到隔离业务的微秒成本。

回收证据限于每组完成/取消检查后释放输入并 GC，以及现有取消/并发隔离回归。长时间连续流、多个大请求在处理期间陆续取消后的独立进程内存曲线没有完整采集，不能据此宣称所有负载下均无泄漏。完整 HTTP 也只完成单并发；后续在系统承诺额度充足的条件下，仍需补齐并发 HTTP 与长期回收测量。

另行采集的 31 MiB 单并发完整编解码 CPU profile 中，`Compiled.EncodeRequest` 占 66.56%，入口 `Compiled.DecodeRequest` 占 21.01%，`CompiledConversion.Request` 占 6.37%。原生协调 `preserveMappedNative` 占 42.33%，**它包含在 EncodeRequest 内，不能再相加**。这是包含初始/收尾及取消检查的 CPU 抽样，不是三段独立计时；profile 运行不计入正式耗时中位数。热点已经主要转向出站编码及原生协调，后续应针对其重复解码、编码和 Value 字节复制建立新的差分基线。

macOS 原生生命周期、下载、更新、回滚，真实供应商和原用户长对话/实际客户端均未验收。本轮没有 Swift 修改；六目标构建不能替代这些验收。此前全项目人工审读台账未完成的部分也不由本轮测试关闭。
