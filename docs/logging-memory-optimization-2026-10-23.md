## 1. 结论

本批比较 **`b9968171` → `9f6be4b8`**，编译器保持 **`2.0.0-dev.77`**。后续测试、清单和文档提交没有新的生产改动。

**主要收益是减少日志处理期间反复申请的大缓冲。31 MiB 样本保存正文的累计分配下降约 32.2%，媒体外置下降约 22.8%；峰值也有改善，但单并发正文的改善没有稳定达到 15%。延迟总体接近，部分结果存在方向反转，不能宣称普遍提速。**

- 初候选曾出现明确媒体回退。问题定位到 Sonic 排序迭代器池保留借用 JSON 树的引用；补上键独立化和私有树清理后重新完成正式矩阵。初候选数据保留，未混入最终结果。

## 6. 改了什么，以及初候选为何回退

### 6.1 条件 HTML 编码

[usage_json.go](../backend/server/usage_json.go) 新增私有 `marshalUsageJSON`。配置保留 `ConfigStd` 的排序、Marshaler 压缩、字符串校验等行为，仅将 HTML 后处理改为条件执行：先编码一次，搜索实际 `<`、`>`、`&`、U+2028/U+2029，命中才调用 Sonic 原 HTML 转义函数。标准库兼容实现预先走旧路径，不在失败后重新编码。

大 base64 正文通常没有这些字符，原实现仍会申请第二份大 HTML 缓冲。本批减少的是这份无必要的缓冲，不是取消 HTML 转义。非法 UTF-8 修正与 HTML 转义交换顺序的等价性通过字节差分及 fuzz 约束；封装不增加相对 `ConfigStd.Marshal` 的自定义 Marshaler 调用次数，普通构建为1次，原生race构建为2次，原错误链保持。

长期日志正文仍经 `string(encoded)` 独立保存，整条记录仍为 `[]byte`。没有重新引入此前 `MarshalToString` 长期保留过大容量的问题。[usage_sqlite.go](../backend/server/usage_sqlite.go) 与事件数组物化复用同一编码入口。

### 6.2 缩短中间复制链

[usage.go](../backend/server/usage.go) 的私有 `sanitizeBodyText` 允许已有不可变字符串直接进入清洗；日志清洗使用借用解码，正文在同步处理期间共享输入，不再为每个 JSON 字符串另复制一份。[gateway_protocol.go](../backend/server/gateway_protocol.go) 的出站正文日志复用已有线格式字符串。

[downstream_capture.go](../backend/server/downstream_capture.go) 的缓冲响应直接复制需要保存的有效范围，不先复制整份响应到另一个捕获缓冲再转字符串。流式捕获的复制、限额和截断语义不变。

普通拥有式 `decodeUsageJSON`、通用 `encodeUsageJSON` 的调用者契约保持原样。媒体独立载荷、脱敏后截断、数字精度和日志四段结构均保留。

### 6.3 失败初候选必须保留

初候选 `fd37c3b8` 已显著减少分配，但 8 MiB 媒体组出现一致回退：

| 指标 | 初候选测量：基线 → 初候选 |
|---|---:|
| 累计分配 MiB/请求 | 107.58 → 83.21（−22.7%） |
| CPU ms/请求 | 70.31 → 54.69（−22.2%） |
| 完整消费 ms | **82.95 → 107.43（+29.5%）** |
| 采样堆峰值 MiB | **102.95 → 131.41（+27.6%）** |

31 MiB 正文初候选分配下降 32.2%，堆峰值却仅从 473.14 → 452.22 MiB，下降 4.4%。这再次证明累计分配不能替代峰值验收。

原始 [formal/runs](../.tmp-dev/logging-memory-optimization-2026-10-23/formal/runs/) 保留 **220 条运行记录**。[summary-formal.json](../.tmp-dev/logging-memory-optimization-2026-10-23/summary-formal.json) 是运行期间生成的早期派生快照，收录 177 条；不能将其余未收录条目当作失败或丢失。本文的初候选示例来自该快照，最终矩阵来自单独的 `formal-final`。

代码审查确认了以下引用链：

```text
Sonic 排序迭代器池
  → MapIterator 的键值数组
  → 借用的短 map key
  → 完整输入正文

同一迭代器
  → Go 1.27 map 兼容迭代器
  → 已解析的 map／元素槽
  → 借用字符串
  → 完整输入正文
```

Sonic v1.15.4 的 `internal/encoder/alg/mapiter.go` 中，`IteratorStop` 只将迭代器放回池；排序项保存原 string 头及 map 槽指针，重用时也没有清空底层数组全部旧项。Go 1.27 兼容迭代器在遍历结束后仍持有 map。仅把媒体值替换成占位符、检查返回日志与资产不借用输入，并不能切断这些隐藏引用。

`9f6be4b8` 在既有私有清洗边界新增 `encodeBorrowedUsageJSON`：

1. 首次编码前收集每个 map 的键，删除并以独立键重插，避免池内的键副本引用整份正文。
2. 编码结束后，通过 defer 递归清空私有树；先将 map 元素槽置 nil，再清 map；数组清空所有槽。
3. 编码输出已独立拥有字节／字符串，清理不修改输出；错误路径同样清理，原始输入仍可用于原 fallback。

没有修改依赖、关闭排序、强制 GC 或清空全局池。该方案只用于本次解码得到的私有无循环 JSON 树，不能推广为销毁任意调用方对象的通用编码器。

依赖引用链是源码可证实的原因；它对时延和峰值贡献多少仍受 GC 时机影响，不把初候选所有波动都归因于同一个池。最终版本已重新完成本报告的正式和确认矩阵。

## 8. 独立登记的正确性问题与剩余成本

### 8.1 既有媒体 memo 指纹不能证明内容相同

[usage_assets.go 的 fingerprint/registerMemo](../backend/server/usage_assets.go) 用“长度＋首 48 字节＋尾 48 字节”命中同请求缓存。两个等长媒体只要首尾相同、中间不同，就可能命中同一个占位符，且命中发生在完整解码和 SHA-256 登记之前。增加长度不能消除这种确定性碰撞。

这是**既有日志媒体保真问题**，本批未修复；不能把缓存命中当作完整内容等价证明。它作用于日志的媒体外置副本，不意味着本批改写了发送给供应商的图片。应另行建立同长度同首尾、不同中间内容的夹具，再设计完整内容验证和兼容性修复，不能为了让本批性能结果更好而忽略或扩大这类复用。

### 8.2 SQLite TEXT 参数仍有整记录副本

[usage_sqlite.go](../backend/server/usage_sqlite.go) 仍生成完整 `[]byte` 记录；[storage/usage_logs.go](../backend/storage/usage_logs.go) 仍用 `string(payload)` 作为 TEXT 参数。大记录包含入站和出站两份正文时，这次复制仍可能接近 62 MiB。此项未在本批消除。

现代 SQLite 驱动还有自己的绑定复制和页缓存，其中 Windows 原生分配不完全反映在 Go `TotalAlloc` 中。不能仅为了减少 Go 分配将参数换为 BLOB，也不能降低 WAL／`synchronous=FULL` 或拆开原子事务。

### 8.3 活跃日志、批次和大键仍有保留边界

- 最终 HTTP 发送完成前，整理后的日志正文和媒体仍由活跃请求持有。128 MiB 异步队列预算不覆盖尚未入队的记录，也不覆盖所有临时编码或 SQLite 内存。
- writer 仍先准备整批记录，再在同一事务中写入；原日志字符串、编码结果和当前绑定参数可能同时存活。不能靠提前丢弃正文或改变重试／事务语义来降低测量值。
- 独立化键解除“小键拖住整份输入”的问题，但如果键本身很大，池仍可能暂存该大键的独立副本。本批不承诺消除所有池保留。
- 新增键克隆和私有树清理也有工作量；不能以代码更短、分配更少替代小请求、节点多、错误分支和完整 HTTP 验收。
